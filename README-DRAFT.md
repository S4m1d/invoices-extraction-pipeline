# Invoices data extractor pipeline 
This is a study project for building data extraction pipeline from invoices.
The result of processing of invoice documents is procurement table.
It is study-only, for generation of synthetic data-set I use https://github.com/kashodev/docsynth, I generate data-set for tests manually.
For mvp it is text-based clean invoice pdfs, so no OCR needed for now.
Pipeline steps: ingestion -> layout analysis -> text extraction from pdf -> fields extraction into json schema -> integration (insert into procurement table)
## Pipeline modules
I'm splitting and pivoting pipeline steps into modules/microservices connected with rabbit mq.
All infrastructure runs in docker containers
### Ingestion
Simple REST API service with POST request that intakes documents and puts them to queue.
Stack: Golang.
### Layout analysis and fields extraction
Microservice that intakes pdf, understands layout and extracts text preserving layout into markdown file.
Stack: Python, pdfplumber.
Bounds: for now it will be only clean text pdfs
### Fields extraction
Microservice that takes markdown file with extracted layout and text and extracts concrete information pieces into json schema.
Then passes this json upstream.
Stack: Python, Pydantic, anthropic python sdk, openai LLM.
### Integration
Microservice that puts info into procurement table and maybe another info into another tables added later.
Stack: Golang, postgresql
#### Procurement table layout
Simple procurement table with few fields like: amount, tax rate, item description, quantity, name of the supplier, dates, etc, nothing elaborate like purchase order id
- invoices
- invoice_lines
There is one-to-many relations between invoice and invoice_lines
# Testing
For tests I need to make evaluation against golden set stored in db file generated by docsynth along with synthetic invoices.
## Testing client
client app for testing pipeline.
- capable of giving different load in parallel.
- shows history of test runs
- user can select which dataset to use for run
- user can navigate to failed run and inspect in details where things went wrong, open file which pipeline failed to process or processed incorrect
### Backend
Does all the work, interacts with dbs, sends request to pipeline in parallel, makes analytical queries.
Stack: Rust, duckdb(for reading .db file with golden set which docsynth produces), sqlite (for storing results of test runs), postgresql (for connecting for the real's application database with procurment table)
### Frontend
Thin client, only visualizes what backend gives to it.
Stack: JS, Slint
